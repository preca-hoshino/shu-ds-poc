# 工具调用（`tool_calls`）

> 返回 [项目 README](../README.md) · [文档索引](README.md)

## 原生不可得（实测）

上游是应用级接口（FastGPT 部署的分享链），模型本身不直接暴露：

- 客户端传的 `tools` 无处可传 —— `/v1/chat/completions`、`/api/v1/*` 实测全 404，
  `/api/core/ai/model/list` 403（需登录）；
- 分享链里只挂了一个 AI 节点（流式只有 `workflowStart` + `chatNode`），没有工具节点。

## 代理侧：提示词模式

`tools` 非空时，[`proxy/toolcall.py`](../proxy/toolcall.py) 按 FastGPT 的 `promptCall` 协议接管：

| 环节 | 做法 |
| :--- | :--- |
| 注入 | 工具声明（只留 `name` / `description` / `parameters`）以 JSON Schema 追加进 `system`，附输出格式与 few-shot 示例（已有 `<ToolSkill>` 段则不重复注入；没有 `system` 就补一条） |
| 多轮还原 | `assistant.tool_calls` → `1: {"name": …, "arguments": {…}}`；纯正文 → `0: …`；`tool` 角色 → `user` + `<ToolResponse>…</ToolResponse>`（上游只认 system/user/assistant） |
| 解析 | `1:` → 规范 `tool_calls` + `finish_reason: "tool_calls"`；`0:` / 无前缀 → 正文。JSON 用宽松解析（``` 围栏、前后带废话、`arguments` 给成字符串都能吃下），**解析失败退回正文，不吞内容** |
| 流式 | `0:` 只在开头多等几个字符（前缀剥掉后照常流）；`1:` 整段缓冲到 JSON 完整再成帧；协议标记**不会漏进可见正文** |

注入的提示词**倾向让模型使用工具**（`优先调用工具`、`涉及实时/校内/个人数据必须调用`、
`参数尽量从上下文推断，不要反问用户`），只保留一个出口：问题与所有工具明显无关时才直接回答。
用 `--no-tool-call` 可完全关掉这套机制（`tools` 回到“接受但忽略”）。

请求示例（[`docs/scripts/test_toolcall.py`](scripts/test_toolcall.py) 里有完整可跑的版本）：

```bash
curl http://127.0.0.1:3000/v1/chat/completions \
  -H "Authorization: Bearer $PROXY_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"deepseek-v3","messages":[{"role":"user","content":"杭州今天天气怎么样？"}],
       "tools":[{"type":"function","function":{"name":"get_weather",
         "description":"查询指定城市的天气",
         "parameters":{"type":"object","properties":{"city":{"type":"string"}},
                       "required":["city"]}}}]}'
```

返回的就是规范形状（`content` 为 `null`、`finish_reason` 为 `tool_calls`）：

```jsonc
{
  "choices": [{
    "index": 0,
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "id": "call_…", "type": "function",
        "function": {"name": "get_weather", "arguments": "{\"city\": \"杭州\"}"}
      }]
    },
    "logprobs": null,
    "finish_reason": "tool_calls"
  }], "…": "…"
}
```

把 `assistant` 消息连同 `{"role":"tool","tool_call_id":"call_…","content":"…"}` 一起发回来
即可完成一轮工具循环（`content` 允许 `null`，规范如此，代理也接受）。

**实测**（2026-09-24，V3 与 R1 两条链各跑一遍）：

| 场景 | 结果 |
| :--- | :--- |
| 非流式单轮调用 | `finish_reason: "tool_calls"`，参数正确 |
| 回灌工具结果 → 最终回答 | `finish_reason: "stop"`，正文正确，不再调工具 |
| 流式工具调用 | 只出 `tool_calls` 帧、正文为空，`finish_reason: "tool_calls"` |
| 带 `tools` 但无需调用 | 无 `tool_calls`，`0:` 前缀已剥掉 |
| 三工具择一 | 挑中预期的那个，参数名与声明一致 |
| 官方 OpenAI SDK 3.19.0 | 非流式 / 多轮闭环 / 流式全部通过 |

### 提示词倾向性的 A/B 实测

「倾向用工具」那句话不是拍脑袋加的，新旧提示词在 8 条 query 上各跑一遍（V3 / R1 各一次）：

| 模型 | 提示词 | 应调且调 | 应调未调 | 误调（闲聊） |
| :--- | :--- | ---: | ---: | ---: |
| V3 | 旧（中性） | 4/5 | 1 | 0/3 |
| V3 | 新（倾向用工具） | **5/5** | 0 | 0/3 |
| R1 | 旧（中性） | 4/5 | 1 | 0/3 |
| R1 | 新（倾向用工具） | 4/5 | 1 | 0/3 |

- **提升点**：参数缺失且需推断时（「帮我看看我这学期考得怎么样」），旧提示词会**反问用户**
  （6/6 都是「请提供您的学号」），新提示词会去调工具；
- **代价**：新提示词换来的参数是**占位串** —— 同一 query 重复 6 次：旧 6/6 反问，
  新的 5/6 去调用（`{"student_id": "请提供学号"}` / `"用户学号"` 这类），1/6 反问。
  也就是把「反问」换成了「带无效参数调用」——**调用方必须自己校验参数**，
  或者把用户身份/上下文直接给模型（代理不管这块）；
- **没有副作用**：闲聊 / 常识 / 玩笑类 query 的误调率在两组提示词下都是 0/3，
  没出现「为了调工具而调工具」；
- **R1 不受影响**：两组提示词下 R1 都是 4/5，依旧会反问而不调工具。

### 解析的容错（都是压测/实测中碰到的）

- 参数名写成 `parameters` 而不是 `arguments`；
- 输出带 ``` 围栏、JSON 前后带废话；
- **漏写冒号**（`1 {json}`）—— 210 工具档实测出现过 1/112，已当调用处理；
- `arguments` 给成 JSON 字符串而不是对象；
- JSON 真的坏了 → 退回正文，不丢内容。

## 规模压测（工具数量 → 准确率）

提示词模式的通行说法是「工具越多越不准」，这个说法在本代理上做了量化。
工具池用 [`docs/scripts/bench_toolcall.py`](scripts/bench_toolcall.py) 合成：
6 个动词 × 7 个宾语 × 5 个方面 = **210 个工具**，命名与描述刻意保持
「同族前缀、只差一个词」的风格（模拟真实的大型 MCP server）；每条 query 唯一指向其中一个工具。

| 工具数 | 声明字符数 | 调用率 | 选中率 | 幻觉率 | 平均延迟 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 196 | 100% | 100% | 0% | 1.21s |
| 20 | 3.6K | 100% | 100% | 0% | 1.40s |
| 60 | 11.6K | 100% | 100% | 0% | 1.39s |
| 100 | 17.9K | 100% | 100% | 0% | 2.40s |
| 210 | 40.8K | 100% | 100% | 0% | 2.33s |

实测约束：

- **没有「工具变多就变笨」的现象** —— 40K 字符的声明、210 个工具下依然 100% 挑对；
- **没有位置偏差** —— 目标工具在列表前 / 中 / 后 1/3 的选中率都是 100%，不存在
  「中间遗忘」；
- **幻觉率恒为 0** —— 从未编造出工具列表之外的名字；
- **代价在延迟与 prompt** —— 1 → 210 个工具，延迟 1.2s → 2.3s，
  `prompt_tokens` 442 → 25392（字符估算），这才是真正的限制因素（上游上下文上限）。

**一个反例及其结论**：用高并发（5 路、连续 280 请求）压测时，曾出现 30 档 80%、
60 档 47% 的「准确率崩塌」，但全部失败都是**空响应**（上游偶发返回空正文），而非选错工具。
按节奏重跑同一配置即回到 100%，故判定为**上游共享服务的瞬时拥塞**，与工具数量无关。
复现这一点的教训：**压测学校这种共享服务必须限制并发并留节奏，否则量到的是上游负载而不是方案本身**。

> 上述 query 由工具自己的 `description` 构造成，属于「语义明确、唯一指向」的最优情形，
> 实测数据应视为**上界**；真实场景里 query 模糊、多个工具都能沾边时，准确率会明显下降，
> 且「该调工具却没调」无法在代理侧补救。

## 实测约束

- **`parallel_tool_calls` 无效** —— 协议一轮只回一个调用；模型偶尔给出数组时也只取第一个；
- **`tool_choice` 只有 `"none"` 有意义** —— 提示词模式无法强制调用，`"required"` / 具名一律当 `"auto"`；
- **提示词偏「多用工具」** —— 参数缺失时可能带占位值调用而不是反问（上方的 A/B 已量化）；
  想要中性的行为就删掉 `proxy/toolcall.py` 里 `## 工具使用原则` 那一节，
  或干脆 `--no-tool-call`；
- **工具越多越不可靠（有前提）** —— 在「语义明确、唯一指向」的 query 下实测无退化
  （见上方压测），但 query 模糊时的准确率下降没有量化，实际部署建议按需裁剪工具；
- **无法预知模型守不守协议** —— 代理已做兜底（不守协议就原样透传、解析失败退回正文），
  但「该调工具却没调」没有补救手段；
- **不校验参数** —— 代理不对 `arguments` 做 JSON Schema 校验，参数合法性由调用方负责。
